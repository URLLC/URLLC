# Dazi 产品案例提纲

## 问题

海外留学生初到新城市时，常有吃饭、自习、逛展、Citywalk 等即时陪伴需求，但直接在陌生人列表中社交的信任成本很高。

## 产品假设

以“共同参加一场具体活动”作为连接起点，能比泛匹配更快地建立话题、降低陌生沟通压力，并为后续联系提供可解释的信任边界。

## MVP 设计

- 以城市、时间、地点和兴趣标签发现活动。
- 发起人发布活动并自动加入；其他用户报名，数据库在并发场景下拦截超额人数。
- 只有共同参加活动的用户才能发起联系申请；接收方显式接受或拒绝。
- 用 Supabase Auth、Postgres 与 RLS 将身份、数据和权限约束放在服务端执行。

## 我的职责

独立完成产品梳理、交互与视觉设计、Next.js 前端开发、Supabase 数据建模/RLS、活动人数一致性迁移、部署准备与演示验收清单。

## 可在面试中讲的工程决策

1. 将活动人数作为数据库维护的真值：对历史数据回填，并由触发器同步，避免首页、地图和详情页出现不同人数。
2. 用数据库锁与触发器处理并发报名，而不是只依赖前端的“人数已满”判断。
3. 联系申请以“共同活动”为前置条件，并用唯一索引保证同一活动不重复申请。
4. RLS 按最小权限拆分：用户只能改自己的资料，联系申请仅接收者可处理。

## 指标设计（上线后再填真实数据）

- 激活：注册后 24 小时内加入或发布活动的比例。
- 供给：每周有效活动数、每个城市的活动覆盖率。
- 匹配：活动报名率、满员率、联系申请接受率。
- 安全：取消率、举报率、失败报名/权限错误率。

不要虚构上述指标；案例展示时说明它们是上线后的验证指标。
